# Milestone 0: Walking Skeleton Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Learning project override:** tasks marked **Owner: G** are written by G, not by an agent. Claude teaches, reviews, and answers questions during those tasks. Only tasks marked **Owner: Claude** may be executed by an agent.

**Goal:** An app that does almost nothing but is completely real: npm workspaces, a tested Express API with a health check and the standard error shape, CI on every pull request, and a live URL on Render.

**Architecture:** One repo with two npm workspaces for now: `shared/` (Zod schemas used by server and, later, web) and `server/` (Express 5). Node 24 runs the TypeScript files directly (type stripping), so there is no build step for the server. `createApp(config)` builds the app without starting it, so tests call it through Supertest and `index.ts` is the only file that listens on a port.

**Tech Stack:** Node 24, TypeScript 6.0, Express 5.2, Zod 4.6, pino 10 + pino-http 11, Vitest 5, Supertest 7, ESLint 10 + typescript-eslint 8, Prettier 3, GitHub Actions, Render.

**Spec:** [docs/10-roadmap.md, M0](../10-roadmap.md#m0-setup-and-walking-skeleton), with details from [02-architecture.md](../02-architecture.md), [04-api.md](../04-api.md#42-errors), [08-testing-quality.md](../08-testing-quality.md), and [09-deployment.md](../09-deployment.md).

**Verified:** every file in this plan was built and run in a scratch copy on 2026-09-10: format, lint, typecheck, and tests all pass after Task 4 (10 tests) and after Task 5 (15 tests), and the running server answered `curl` correctly.

## Global Constraints

- Node `24.x` (the `engines` field in the root `package.json`).
- TypeScript `~6.0.0`. Not 7.0: typescript-eslint 8.70 requires TypeScript below 6.1 (decision D18).
- ES modules everywhere (`"type": "module"`).
- Only "erasable" TypeScript: no `enum`, no `namespace`, no constructor parameter properties like `constructor(readonly status: number)`. The `erasableSyntaxOnly` setting enforces this.
- Relative imports end in `.ts`: `import { loadConfig } from "./config.ts";`
- Every API URL starts with `/api/v1`.
- Every error response uses the shape from [04-api.md section 4.2](../04-api.md#42-errors): `{ "error": { "code", "message", "requestId", "details"?, "meta"? } }`.
- One task = one branch = one pull request. Commit messages use Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
- `.env` is never committed.

### Task 3: Configuration from environment variables

**Owner:** G

**Concept.** Settings that change between laptop and production (port, log level, later the database URL) come from **environment variables**, not from code. `process.env` is an object of strings, and anything can be missing or misspelled. So we read it **once at startup** and check it with a Zod schema. If something is wrong, the server refuses to start and names the bad variable, instead of crashing later on some user's request. `z.coerce.number()` turns the text `"8080"` into the number `8080`.

**Files:**
- Create: `server/src/config.ts`
- Test: `server/test/config.test.ts`

**Interfaces:**
- Produces: `loadConfig(env?: NodeJS.ProcessEnv): Config`. With no argument it reads `process.env`.
- Produces: `type Config = { NODE_ENV: "development" | "test" | "production"; PORT: number; LOG_LEVEL: "fatal" | "error" | "warn" | "info" | "debug" | "trace" | "silent" }`
- Defaults: `NODE_ENV` `"development"`, `PORT` `3000`, `LOG_LEVEL` `"info"`.

- [ ] **Step 4: Write `server/src/config.ts` yourself**

What it needs:
1. A Zod object schema with the three variables, their allowed values, and their defaults.
2. `loadConfig(env = process.env)` that uses `safeParse` (not `parse`), so you control the error message.
3. On failure, throw an `Error` whose message lists every problem as `NAME: what's wrong`. The problems are in `result.error.issues`; each has a `path` array and a `message`.
4. Export the `Config` type with `z.infer`.

Hints: `z.enum([...]).default(...)`, `z.coerce.number().int().min(1).max(65535)`.

<details>
<summary>Reference solution (open after a real attempt)</summary>

```ts
import { z } from "zod";

const EnvSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  LOG_LEVEL: z.enum(["fatal", "error", "warn", "info", "debug", "trace", "silent"]).default("info"),
});

export type Config = z.infer<typeof EnvSchema>;

// Reads settings from environment variables once, at startup.
// Bad or missing values stop the server immediately with a clear message.
export function loadConfig(env: NodeJS.ProcessEnv = process.env): Config {
  const result = EnvSchema.safeParse(env);
  if (!result.success) {
    const problems = result.error.issues
      .map((issue) => `  ${issue.path.join(".")}: ${issue.message}`)
      .join("\n");
    throw new Error(`Invalid environment variables:\n${problems}`);
  }
  return result.data;
}
```

</details>

### Task 4: The app, a request ID, logs, and the health check

**Owner:** G, guided closely (the first real Express code).

**Concept.** A request passes through a chain of **middleware**: functions shaped `(req, res, next) => { ... }`. Each one does one job, then calls `next()` to hand the request to the next function in line. Ours, in order:
1. `requestId` gives each request a unique ID and sends it back in the `X-Request-Id` header.
2. `pino-http` writes one JSON log line per request, tagged with that ID.
3. The router matches `GET /api/v1/health`.

`createApp(config)` **builds** the app, and `index.ts` **starts** it. Tests import `createApp` and never open a real port.

**TypeScript detail:** `req.id` isn't part of Express's own types. The `pino-http` package adds it to the request type, which is why `requestId.ts` can set it once `app.ts` imports `pino-http`.

**Files:**
- Create: `server/src/middleware/requestId.ts`, `server/src/logger.ts`, `server/src/modules/health/routes.ts`, `server/src/app.ts`, `server/src/index.ts`
- Test: `server/test/health.test.ts`

**Interfaces:**
- Consumes: `loadConfig`, `Config` (Task 3); `HealthResponse` (Task 1)
- Produces: `requestId: RequestHandler`, `createLogger(config: Config): pino.Logger`, `healthRouter: Router`, `createApp(config: Config): Express`

- [ ] **Step 4: Write `requestId` yourself**

`server/src/middleware/requestId.ts` exports `requestId`, typed as Express's `RequestHandler`. It must:
1. Make an ID with `randomUUID()` from `node:crypto`.
2. Store it on `req.id`.
3. Set the `X-Request-Id` response header (`res.setHeader`).
4. Call `next()`. Forget this and every request hangs forever. Try it once on purpose later.

<details>
<summary>Reference solution</summary>

```ts
import { randomUUID } from "node:crypto";
import type { RequestHandler } from "express";

// Gives every request a unique ID, so one request's log lines and error can be matched up.
export const requestId: RequestHandler = (req, res, next) => {
  const id = randomUUID();
  req.id = id;
  res.setHeader("X-Request-Id", id);
  next();
};
```

</details>

### Task 5: Errors in the standard shape

**Owner:** G

**Concept.** When something goes wrong, every endpoint must answer with the same JSON shape ([04-api.md 4.2](../04-api.md#42-errors)), so the frontend can handle every error with one piece of code. Two kinds of errors:
- **Errors we throw on purpose** (`AppError`): "not found," "not enough money." Their status, code, and message are safe to show.
- **Bugs** (any other `Error`): always answered as `500 internal_error` with a generic message. The real message might contain secrets, so it only goes to the logs.

Express 5 sends anything thrown in a route to the **error handler**: the middleware with **4** parameters `(err, req, res, next)`. A `notFound` middleware placed after all routes catches URLs that matched nothing.

**Files:**
- Create: `server/src/lib/errors.ts`, `server/src/middleware/errorHandler.ts`
- Modify: `server/src/app.ts` (add the last two `app.use` lines)
- Test: `server/test/errors.test.ts`

**Interfaces:**
- Consumes: `requestId` (Task 4), `createApp`, `loadConfig` (Tasks 3 and 4), `ErrorResponse` (Task 1)
- Produces: `class AppError extends Error` with `constructor(status: number, code: string, message: string, meta?: Record<string, unknown>)` and readonly fields `status`, `code`, `meta`
- Produces: `class NotFoundError extends AppError` with `constructor(message?: string)`, always `404` / `"not_found"`

- [ ] **Step 4: Write the error classes yourself**

`server/src/lib/errors.ts`: `AppError` extends `Error` and stores `status`, `code`, and `meta`; `NotFoundError` extends `AppError` with a default message. Because of `erasableSyntaxOnly`, you can't use the `constructor(readonly status: number)` shortcut. Declare the fields, then assign them in the constructor. Set `this.name = "AppError"` so logs show a useful name.

<details>
<summary>Reference solution</summary>

```ts
// An error we throw on purpose. The error handler turns it into the standard JSON error.
export class AppError extends Error {
  readonly status: number;
  readonly code: string;
  readonly meta: Record<string, unknown> | undefined;

  constructor(status: number, code: string, message: string, meta?: Record<string, unknown>) {
    super(message);
    this.name = "AppError";
    this.status = status;
    this.code = code;
    this.meta = meta;
  }
}

export class NotFoundError extends AppError {
  constructor(message = "We couldn't find that.") {
    super(404, "not_found", message);
  }
}
```

- [ ] **Step 5: Write `notFound` and the error handler yourself**

`server/src/middleware/errorHandler.ts`:
1. `notFound` (a `RequestHandler`) passes `new NotFoundError("That route doesn't exist.")` to `next(...)`. Passing something to `next` is how middleware says "this is an error."
2. `createErrorHandler(logger)` returns an `ErrorRequestHandler` with **four** parameters `(err, req, res, _next)`:
   - If `err` is an `AppError`, use it. Otherwise make `new AppError(500, "internal_error", "Something went wrong on our side. Please try again.")`.
   - If the status is 500 or more, log the **original** `err` with `logger.error(...)`, including `requestId: req.id`.
   - Respond with that status and an `ErrorResponse` body: `code`, `message`, `requestId: String(req.id)`, and `meta` only when there is some.

<details>
<summary>Reference solution</summary>

```ts
import type { ErrorResponse } from "@g-bank/shared";
import type { ErrorRequestHandler, RequestHandler } from "express";
import type { Logger } from "pino";
import { AppError, NotFoundError } from "../lib/errors.ts";

// Runs when no route matched the URL.
export const notFound: RequestHandler = (_req, _res, next) => {
  next(new NotFoundError("That route doesn't exist."));
};

// Express treats a middleware with 4 parameters as the error handler.
export function createErrorHandler(logger: Logger): ErrorRequestHandler {
  return (err, req, res, _next) => {
    const appError =
      err instanceof AppError
        ? err
        : new AppError(
            500,
            "internal_error",
            "Something went wrong on our side. Please try again.",
          );

    if (appError.status >= 500) {
      logger.error({ err, requestId: req.id }, "unhandled error");
    }

    const body: ErrorResponse = {
      error: {
        code: appError.code,
        message: appError.message,
        requestId: String(req.id),
        ...(appError.meta ? { meta: appError.meta } : {}),
      },
    };
    res.status(appError.status).json(body);
  };
}
```

</details>
